# v0 acceptance record

Status: **v0 release candidate for supervised local use**. Source, isolated wheel installation, active Stop hook invocation, native reviewer activation, and controlled behavior have observable evidence. This is not a claim of general reviewer quality superiority or readiness for unattended global installation. The prior isolation study did not select a quality winner.

1. **Active runtime:** Native subagents actually received frozen packages and returned hash receipts and structured findings in this Codex session. The Python CLI runs from an isolated installed wheel. An isolated Codex CLI invocation loaded the optional Stop hook through a vetted one-off configuration and recorded a continuation. Persistent trust in the user's project has not been installed.
2. **Canonical state:** Executable state distinguishes parent obligations, work items, delegation, integration, decisions, epistemic classes, authority, and chronology. Twenty-two deterministic tests cover key transitions and gate distinctions. New authority state remains unspecified until the actual policy is recorded. Concurrent writer merge semantics are not implemented; one integrator serializes updates.
3. **Complete chronology:** The package builder rejects noncontiguous chronology and includes both failed and later passing test events. It depends on the coordinator recording every relevant event; missing source events cannot be reconstructed.
4. **Built-in activation:** Seven fresh controlled children, a repair reviewer, and at least ten current-work implementation reviewers returned matching package hashes. The F063 live-derived reviewer also returned a matching hash. The `reviewer_activated`, `package_received`, and `package_hash_verified` events are persisted in case ledgers. Initial reused-child diagnostics are excluded from the fresh score.
5. **Detection families:** F062 lifetime, unsupported decision reversal, false completion evidence, unnecessary compatibility, unrelated feature, and stale failure all drew relevant findings. Exact grader criterion matched in four of six defect cases.
6. **False positives:** The one concrete v2 clean case drew none. The underspecified v1 clean pilot drew a plausible finding, demonstrating fixture sensitivity. Operational false-positive rate is UNKNOWN.
7. **Review→repair:** One F062 defect was removed and a fresh reviewer returned zero findings. One demonstration cannot establish a general defect-reduction rate or regression rate.
8. **Completion gate:** It refuses local worker completion without integration, missing obligations or resolving evidence, stale latest failures, revision-mismatched verification, a pending review, an older review of a different candidate, untargeted repair evidence, unresolved findings, and missing consumer checks when required. External blockers return `BLOCKED` when no independent work remains; otherwise the task stays `CONTINUE`. The Stop hook requests one continuation for every `CONTINUE` result, including when only a gate reason remains. The `stop_hook_active` guard prevents immediate looping. Excess continuation on fresh work is not yet measured.
9. **Multi-worker compatibility:** Work items and delegated returns are separate from the parent and integration. Worker topology is represented; parallel write conflict resolution is left to a single integrator and has not been stress-tested.
10. **Real-work quality:** F063-LIVE's original prompt, candidate, metadata, and raw trace were repackaged as one live-regression-derived case; its reviewer found no defect and left underlying source inspection unknown. The current implementation is a second actual current-work episode. Its first ten review rounds found 4, 2, 2, 2, 2, 1, 2, 1, 2, and 1 blocking defects. The tenth identified missing itemized completion obligations, which are now tracked individually in the ledger. Later review results and release state are recorded in the case ledger and run index. This does not quantify quality gain across independent user tasks.
11. **Cost:** The previous isolation study measured substantial token and wall-time costs, but those are historical. This v0 run did not expose reliable per-child token usage, and installed runtime overhead is not quantified.
12. **Release decision:** Use as a supervised local release candidate with explicit ledger setup and native reviewer dispatch. Do not promote to an unattended global hook or infer superiority over separate reviewer invocation from these cases.
13. **UNKNOWN before v1:** Major blocker sensitivity and calibration, repeated-run false positives, cross-context leakage, automatic native child transport from Python, persistent hook trust in the user's project, concurrent ledger writers, and full runtime cost.
