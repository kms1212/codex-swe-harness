# Evaluation method

The master rubric is the prior 15-item artifact checklist. The controlled set under `evals/challenges.py` begins with one concrete clean orders integration design, then adds one defect at a time: transient work status in durable design (F062 family), unsupported decision reversal, false validation completion, gratuitous version/legacy mode, unrelated feature, and stale failure. `grader-labels.json` stays outside reviewer-visible packages. Seven v2 packages were frozen and reviewed by seven fresh native children. Four initial responses across the native runs violated the result schema (three severity enums and one confidence type); the validator rejected them and the same reviewers reformatted without new evidence. The diagnostic v1 fixture is retained because its underspecified clean design drew a plausible finding; it is excluded from v2 quality metrics.

This document describes the historical evaluation corpus, not current runtime acceptance.

Historical comparison evidence is in `eval-results/prior-evidence/FINAL-DECISION.md`. Its 34 paired runs and F062 miss motivate this challenge but are not fresh v0 performance data. One real-work-derived case reuses the F063-LIVE prompt, result, metadata, and trace from the base-selection study. The second case is this implementation's current candidate and actual correction cycle. F063 is a live-regression fixture, not an independent new user task; this distinction is retained in the scores.

Metrics are reported separately for reviewer detection, false positives, schema validity, activation, repair, completion, state retention, and runtime cost. Exact criterion recall is 4/6 controlled defects; all six drew at least one relevant finding, but two used adjacent rubric criteria. The clean case drew zero findings. This tiny constructed sample cannot estimate operational false-positive rates or major blocker sensitivity. Broader promotion requires independent exact-start real-work episodes, adjudicated defects, consumer outcomes, stable activation, and cost measurement. The present artifact is a supervised local release candidate only.

The repository retains this corpus for reproducible rubric calibration, regression evaluation and provenance: controlled candidate/package/result triples are consumed by `evals/validate_fresh.py` and `evals/challenges.py`; raw traces and review dumps support hash receipts and run-index audits through `evals/index_raw.py` and `evals/index_native_traces.py`. Real-work ledgers and acceptance records explain historical findings and repairs, not current source behavior. Generated fixtures are deliberate evaluation inputs or immutable outputs of these named runs. Traceability documents and source-to-runtime records are historical evidence, not maintained implementation specifications. Maintainers of the evaluation corpus own these records. New task reports and sessions do not inherit this retention policy: use the task ledger unless a specific new regression/provenance consumer justifies a corpus addition. Do not rerun old one-off review preparation/repair scripts against frozen history as current acceptance.
