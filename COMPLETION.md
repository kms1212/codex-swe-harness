# Parent completion and liveness

`evaluate_completion` returns `COMPLETE`, `CONTINUE`, or `BLOCKED`. It checks declared parent obligations with resolving evidence refs, work item integration, delegated result consumption, integration conflicts/dependencies, required latest verification by scope and candidate revision, consumer-point evidence, native semantic-review activation, pending review receipt, and unresolved blocking findings. The latest semantic review must cover both the current candidate revision and the current relevant task, epistemic, authority, work, integration, blocker and artifact context. An accepted blocking finding needs a PASS after that review's verification cutoff, explicitly targeted to the finding with `resolves`; consumer-verification findings also need `consumer_point`. A stale failure is retained in chronology but the latest result for the same scope and revision determines current verification. A later failure or candidate revision or semantic-context change reopens the gate.

`CONTINUE` includes machine-readable reason codes and remaining obligations. An external blocker yields `BLOCKED` only when all remaining work or parent obligations are explicitly linked to that external blocker, with no integration or local gate repair available. Declaring obligations, integrating a completed worker result, fixing a failed verification, or obtaining consumer evidence keeps the task in `CONTINUE` even if an unrelated external blocker exists. `BLOCKED` lists required external inputs. `COMPLETE` includes evidence refs. An empty obligation set, no candidate revision, or no required verification/consumer scope prevents completion. The gate cannot infer missing requirements from a free-form objective or independently prove that a claimed artifact revision matches bytes on disk; the integrator must supply that hash.

`progress_snapshot` separates available next work and unresolved blockers from repeated same-command/scope/result actions. Repetition is a prompt for strategy review, not proof of no progress. `Stop` is the documented Codex lifecycle hook capable of requesting continuation. The optional hook in `runtime/stop_hook.py` requests continuation for every `CONTINUE` gate result when `stop_hook_active` is false, choosing a ready work item if present or the first gate reason otherwise. The active-hook guard prevents an immediate continuation loop within the same turn. An isolated CLI run observed the continuation; persistent project trust is intentionally separate.
