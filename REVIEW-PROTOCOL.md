# Semantic review protocol

`ReviewEvidencePackage` version 1 contains package/task IDs, original request, confirmed requirements and active decisions, complete decision history including superseded records, a semantic-context hash over all reviewed task, epistemic, authority, work, integration, blocker and artifact state, candidate refs/diff/resulting state, complete verification chronology, unresolved state, rubric projection, and source refs. Canonical UTF-8 JSON uses sorted keys, compact separators, and a trailing newline; SHA-256 of those exact bytes is the receipt. A second review freezes a new package ID and hash rather than rewriting the first.

`route_review` selects criteria from the 15-item master rubric by change type. The active Stop path combines current changed paths, deterministic-diff evidence, and semantic risk before deciding whether review is useful. Multi-file integration, architecture or specification changes, compatibility decisions, and meaningful user-artifact semantics route to review; deterministic trivial edits and local code with direct verification can use narrower checks. A previous candidate's review requirement does not automatically apply to a later candidate. A pending frozen review and unresolved findings remain obligations. The routing decision is an event distinct from a reviewer verdict.

`SemanticReview.review(package, projection) -> ReviewResult` is the transport-neutral contract. A result has review ID, package hash, adapter, findings, overall completion risk, and unknowns. Findings carry criterion, minor/major/critical severity, evidence refs, violated requirement, blocking flag, and confidence. Empty findings are valid. The built-in adapter prepares the frozen file and a native handoff request; the coordinator instantiates a fresh semantic-evaluation child, records package receipt/hash/role evidence, and ingests only schema-valid results. A malformed result is a review-result failure, separate from activation failure or a supported no-defect judgment.

The execution fabric owns dispositions (`accepted`, `partially_accepted`, `rejected`, `unresolved`), repair, and subsequent verification. Dispositions reference evidence in the ledger. `prepare` marks the package hash pending in canonical state; ingest clears it only after schema-valid receipt. A review records candidate revision and verification cutoff. Repaired blocking findings require a later PASS whose `resolves` list names that exact review ID and finding index; consumer-verification findings require `consumer_point`. Repeated findings remain traceable through separate review IDs and chronology. The current adapter requires the coordinator to pass observed native child identity and receipt; the bridge cannot attest independently that the child's context contained only the package.
