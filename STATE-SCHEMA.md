# Canonical state schema

`state.json` is schema version 1. `events.jsonl` is append-only with monotonic sequence, kind, data, and state hash on mutations. The state snapshot and event stream are harness-owned for the task lifetime. Review packages and evaluation outputs are immutable historical artifacts once frozen.

`TaskState` stores objective, original request, obligations, blockers, work items, delegated work, integration, and completion. A blocker may name `work_item_ids` and `obligation_ids` to identify the work and parent commitments that an external input prevents. A worker's `DONE` does not imply integration: work items must become `INTEGRATED`, candidate changes must appear in integrated changes, delegation must be `CONSUMED`, and required integration and consumer checks must pass.

`DecisionState` stores decision, status, scope, evidence refs, supersedes, and superseded-by. New superseding decisions update the old decision's reverse link and status. `EpistemicState` uses `FACT`, `INFERENCE`, `UNKNOWN`, and `USER_ASSERTION`. Facts and inferences need evidence refs; conclusions should record changed evidence, reasoning correction, requirement change, or external-state change in the event log.

`AuthorityState` starts as `unspecified`, with null default admissibility and closure. The integrator records the task's actual policy before relying on it. Explicit policy models include allowlist, denylist, capability set, mixed, schema-constrained, and state-machine-constrained policies with default admissibility, closure, scope, capabilities, constraints, exceptions, side-effect scope, and delegation scope. A closed allowlist/capability set cannot silently become an open denylist. This preserves the F063 policy-model requirement without assigning a policy before it is known.

`EvidenceState` records producer, operation, observable result, scope, chronology index, and artifact refs. `verification_chronology` stores each action in order, including failures followed by repairs and later passes. `ReviewState` stores the frozen hash, adapter, findings, disposition, resolution evidence, and native activation receipt. `ArtifactContext` records semantic role, owner, lifetime, and current state role.

Instruction edits add their paths and per-file content identities to `completion_state.instruction_recomposition_required` and `instruction_recomposition_targets`. An `instruction_changes` record ties each current identity to the requirement, semantic owner, existing principle, integration or move, displaced guidance, complete-file review evidence, and active consumer check. The gate requires that record and a passing consumer check; harness-managed installations also require a recorded installed revision matching `instruction_source_revision`. Unchanged instructions need no new record. A later edit invalidates only the changed instruction identity.

`completion_state.candidate_revision` identifies the candidate under evaluation. `pending_review_hash` blocks completion between review dispatch and result receipt. Required verification and consumer PASS events must name the same `artifact_revision`. A review records its candidate revision, a hash of reviewed request, requirements, decisions, authority, epistemic/work/delegation/integration/blocker/artifact state and completion requirements, and verification cutoff index; the latest review must cover both the current candidate and current semantic context. Accepted blocking findings need a later passing verification tied to the current candidate and explicitly naming that finding in `resolves` (for example `review-id:0`). Criterion 14 also needs consumer-point evidence. Evidence refs on satisfied obligations must resolve to ledger evidence or verification events.

A scoped verification with `related_inputs` records an `input_identities` map covering those inputs. `completion_state.scope_input_identities` states the current expected map for each required scope. Reuse compares the entire map, so a changed contract invalidates a PASS even when the direct target is unchanged. A record with related inputs but no identity map cannot satisfy the current gate.

The CLI `add` operation creates typed records. `transition` changes work, delegation, obligation, or blocker status with evidence refs. `replace` changes authority, integration, or completion state. Completion replacement cannot clear a required semantic review, clear an adapter-owned pending review, narrow required verification/consumer scopes, or declare `COMPLETE` directly. Event history preserves the prior value. The v0 file ledger is a single-writer process model; it does not implement concurrent writes or conflict-free merging. Parallel workers must return to one integrator that serializes state changes and records worktree/snapshot provenance in evidence and integration refs.
